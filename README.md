## 一、 本组电商场景

本组选择**在线书店电商场景**，专注于纸质书的零售交易，主要交易对象为实体书。
主要服务对象为普通读者、学生及藏书爱好者。

## 五、 架构选型结论

**综合选型结论：本项目最终选定“前后端分离架构”。**

**选型依据：**
综合网上书店场景需求，对比单体架构、前后端分离架构和服务化架构后得出：

1. **成本与周期**：开发成本低于服务化方案，契合当前3~5人小团队规模，能够在项目规定时间内完成。
2. **团队匹配度**：前后端解耦后可并行开发、并行调试（按“两人前端、其余后端”分工），利于团队协作。
3. **可维护性与扩展能力**：相比单体架构，具备更好的可维护性与多端扩展能力（同一套后端API可同时服务PC端、后续小程序/移动端）。
4. **安全边界**：认证、鉴权、数据访问全部收敛在后端API，边界清晰，前端不直连数据库。

该架构有效平衡了开发效率与系统解耦需求，满足当前业务快速迭代要求，为后续架构平滑演进奠定基础。

`bigint_ops.py` 提供四组能力：

1. **模运算基础** —— `mod` / `mod_add` / `mod_sub` / `mod_mul`，负数返回非负代表元；
2. **快速幂（模幂）** —— `mod_pow` 采用重复平方乘，复杂度 O(log e)；
3. **最大公约数与模逆** —— `gcd` / `ext_gcd`（扩展欧几里得）/ `mod_inverse`；
4. **素性检测与素数生成** —— `is_probable_prime`（Miller-Rabin）/ `random_prime`（固定种子可复现）。

运行方式（Python 3.9+，无第三方依赖；模块含自检与性能实测，直接运行即可看到结果）：

```bash
python src/crypto/bigint_ops.py
```

`rsa.py` 实现小位宽（64 / 128 / 256 位）**教科书式 RSA**：

1. **密钥生成** —— `generate_key_pair(bit_length, rnd)`，产出 p、q、n、φ(n)、e、d 及 CRT 参数；
2. **加密 / 解密** —— `encrypt`（`c = m^e mod n`）、`decrypt`（`m = c^d mod n`）；
3. **CRT 加速** —— `decrypt_crt`，约 3 倍提速（1024 位实测 2.78×）；
4. **字符串与中文** —— `encrypt_string` / `decrypt_string`，按模数位宽分块、块首加 `0x01` 哨兵，支持任意长度与中文字符串。

运行方式（会依次输出公开向量自检、固定种子确定性向量、中文用例、边界与非法输入、
CRT 性能对比、以及"小位宽为什么不能用于生产"的分解实测）：

```bash
python src/crypto/rsa.py
```

交叉验证（第二条路径，用标准库 `pow` / `math.gcd` 独立复算，共 128 项断言）：

```bash
python src/crypto/verify_with_stdlib.py
```

> 随机源非密码学安全、小位宽模数可被分解、未含填充不能直接加密数据。

### 怎么建库

后端首次启动会自己建表（`src/user/db.py` 的 `init_db()`），空库状态下直接起后端即可，不需要手工执行 SQL。要重建就从空库开始：删掉仓库根目录的 `auth.db`，再按下一步启动。

> `db/schema.sql` 是另一套 MySQL 表结构（`user_account` 等），与当前 `server.py` 使用的 SQLite 表（`users`、`session_token`）不是同一套，本节的演示流程走 SQLite 这条。

### 怎么起后端

Python 3.9+，只用标准库，无需安装依赖。在仓库根目录执行：

```bash
python -m src.user.server
```

看到 `Server running at http://127.0.0.1:8000` 即为就绪。

### 怎么起前端

另开一个终端，同样在仓库根目录：

```bash
python web/serve.py
```

浏览器打开 <http://127.0.0.1:8080/login.html>。

`web/serve.py` 只监听 `127.0.0.1`，同时把 `/api/` 转发到 `127.0.0.1:8000`。加这层转发的原因是浏览器把不同端口视为不同来源，而后端只实现了 GET/POST，没有应答 `OPTIONS` 预检、也没有 `Access-Control-Allow-*` 头；由前端这一侧转发，浏览器看到的始终是同一个来源，不必为了跨域去改服务端。两个进程仍然是分开起的。

**不要直接双击 html 文件打开**：`file://` 取不到 `/api`，页面会提示连不上服务端。

### 怎么试

1. 打开 `register.html` 填登录名、手机号、口令，提交后提示注册成功；
2. 打开 `login.html` 用刚注册的账号登录，成功后自动进入个人信息页；
3. 个人信息页显示服务端返回的用户标识、登录名、打码手机号、账号状态、注册时间；
4. 打开 `logout.html` 点「确认退出」，再刷新个人信息页，服务端返回 `401`，页面如实显示。

各步失败时的提示：

| 情况 | 服务端返回 | 页面表现 |
| :--- | :--- | :--- |
| 登录名或手机号已存在 | `409 USER_ALREADY_EXISTS` | 该登录名或手机号已被使用 |
| 账号不存在 / 口令错误 | `401 AUTH_INVALID_CREDENTIALS` | 同一句「账号或密码错误」，不区分是哪一种 |
| 没登录就开个人信息页 | `401 AUTH_UNAUTHENTICATED` | 登录状态无效，请重新登录 |
| 令牌被改过、已过期、已退出 | `401 AUTH_UNAUTHENTICATED` / `AUTH_TOKEN_EXPIRED` | 同上，由服务端判定 |
| 提交了契约外的字段 | `400 VALIDATION_ERROR` | 请求内容不被允许 |
| 后端没起 | 转发层连不上 | 提示先在另一个终端启动后端 |

错误提示下方另有一行小字，显示 `错误码` 与 `追踪号`，可与后端日志对上。

### 前端的三条口径

- **令牌放 `sessionStorage`，只走 `Authorization` 请求头，不用 Cookie。** 请求头不会随表单或链接自动携带，CSRF 在本场景由设计规避；不用 `localStorage` 是因为关掉标签页即失效，长期驻留的风险更小。但这只是降低风险，不是安全边界——边界在服务端的验签与过期。
- **页面不判权限。** 个人信息页能不能看，由服务端返回 200 还是 401 决定；前端没有任何「是不是管理员」「该不该显示按钮」之类的判断，也没有靠隐藏入口实现鉴权。页面里的空值检查与两次口令一致性提示只算体验，不替代服务端校验。
- **所有来自服务端的文本都用 `textContent` 写入，不用 `innerHTML` 拼接。** 登录名里塞 `<script>` 也只会显示成文本。

> 仅用于教学演示，不接真实支付、不使用真实用户数据；仓库中不含真实口令、密钥与证书。
