## 1. 判定标准

> 越权：拿 A 的令牌访问 B 的个人信息，返回 404 而不是 403——403 等于告诉对方这个 ID 存在。

三条一起看才算过：

1. 状态码是 **404**，不是 403、不是 200；
2. 响应体与"访问一个根本不存在的编号"**逐字一致**（除 `traceId` 外）；
3. 响应体里**没有 B 的任何字段**（用户名、手机号、昵称一个都不许出现）。

## 2. 为什么 `GET /api/users/me` 单靠自己是测不出越权的

契约 §4.4 把"个人信息"定义为"令牌对应的人"，接口**不接收任何用户标识**，多传参数被忽略并记审计
（A-08 实测：`?userId=2` 仍返回 A 自己）。这是好设计——它从接口形状上就消灭了"传别人的 id"这件事。

但这样一来，"拿 A 的令牌访问 B"就没有入口可测了。为了满足任务书这条可验收的要求，本期增加了
一个**越权验收辅助接口** `GET /api/users/{userId}`：

| 行为 | 返回 |
| :--- | :--- |
| `{userId}` = 令牌本人 | 200，与 `/api/users/me` 同一份结构 |
| `{userId}` ≠ 令牌本人 | **404 RESOURCE_NOT_FOUND**，与"不存在"同形 |
| `{userId}` 非数字 | 400 VALIDATION_ERROR（不落到查询） |
| 不带令牌 | 401（鉴权在前，连存在性都不给判断） |

它是 `/me` 的补充面，不是替代：`/me` 仍是主接口（前端只用它），`/users/{id}` 只用于
"归属校验必须在服务端做一遍"的验收与演示。同时被写进 OpenAPI（标为辅助接口）与交接契约。

## 4. 401 / 403 / 404 的取舍，答辩时会被追问

| 情形 | 返回 | 为什么 |
| :--- | :--- | :--- |
| 没带令牌、令牌无效 | 401 | 先确认"你是谁"，这一步不涉及任何资源 |
| 已登录但访问别人的资源 | **404** | 403 等于确认"这个资源存在"，把编号遍历变成存在性探测 |
| 角色不允许（II 阶段才有） | 403 | 角色是公开语义（"你不是买家"），不泄露任何对象的存在性 |

A-09 与 A-01 摆在一起就是这个次序的证据：匿名先吃 401，登录后再吃 404，
两步都不会告诉对方"编号 2 到底存不存在"。

## 5. 结论与遗留

- 结论：越权访问返回 404、与"不存在"同形、不泄露 B 的字段，且尝试留痕（`authz_denied`）。
  请求体里的 `userId` / `role` 被白名单拒绝，身份只从令牌来。
- 遗留一：本期只有买家一个角色，"角色不允许 → 403"这条分支没有真实场景可测
  （`AUTH_FORBIDDEN` 只在 CORS 预检拒绝时出现）。角色矩阵要到 II 阶段接入
  `app_role` / `user_role_relation` 后才能验收，已在交接契约里列明。
- 遗留二：`/api/users/{userId}` 是本期新增的辅助接口，**II 阶段若要做管理端查用户**，
  应另开 `/api/admin/users/{userId}` 并加角色校验，不要在这个接口上放宽归属判断。
