## 1. 任务书要求的三枪

> 会话劫持：改一个字节的令牌、改令牌里的用户标识、退出后重放旧令牌，三枪都必须被拒。

三枪分别对应 S-01～S-03、S-04、S-06。其中"改令牌里的用户标识"这一枪在本系统里
**没有可改的结构**——令牌是 32 字节随机值的 base64url 编码，不编码用户名、角色或过期时间。
S-04 用"令牌前缀 + `.2`"模拟这种攻击，服务端不解析令牌内容，只拿 SHA-256 摘要查库，直接 401。

## 2. 控制点

| 控制 | 位置 | 说明 |
| :--- | :--- | :--- |
| 令牌无结构 | `tokens.issue()` `secrets.token_urlsafe(32)` | 43 字符 base64url，256 位熵；没有任何可"解出来改一改"的字段 |
| 只存摘要 | `session_token.token_hash` | 库里存 SHA-256，原文只在登录响应出现一次；全表搜原文命中 0（S-08） |
| 单一鉴权函数 | `auth.require_auth()` | 五个受保护端点全部调用它；形状不符直接拒，不查库 |
| 服务端撤销 | `auth_service.logout()` | 写 `revoked_at` + `revoke_reason='logout'`，不依赖客户端删本地副本 |
| 服务端判过期 | `timeutil.is_past(expires_at)` | 过期由库里的时间决定，客户端传什么字段都不影响（未知字段一律 400） |
| 令牌不进 URL | `auth.bearer_from()` 只读 `Authorization` | S-09 把令牌塞进查询串，服务端忽略，仍按请求头鉴权 |

## 4. 三条判定细节

**"401"和"401"不是一回事。** 改一字节返回 `AUTH_UNAUTHENTICATED`（库里查不到这个摘要），
过期返回 `AUTH_TOKEN_EXPIRED`（摘要查得到、时间过了）。两者分开，是因为契约要求过期能让前端
引导重新登录；而"查不到"与"没带"必须同形——否则等于告诉攻击者"这枚令牌曾经存在"。

**S-05 不是漏洞，是对照组。** 拿 B 的令牌当然能看 B 的信息——那是一次合法的 B 的会话。
它证明的是"身份只由令牌决定，请求里给什么都不改变身份"，和 S-04 一起构成"改不了"的完整论证。

**S-07 是改库造出来的过期，不是等两小时。** 现场演示时直接
`UPDATE session_token SET expires_at='2020-01-01T00:00:00.000Z'`，再拿原令牌请求即可，
不需要真的等。这一步在演示脚本里是可复现的。

## 5. 结论与遗留

- 结论：三枪全部被拒，且拒绝发生在**进入业务逻辑之前**——`require_auth()` 在查 `user_account`
  之前就把令牌挡掉了（SR-07 要求"不产生用户数据查询"），库里只存摘要，退出撤销在服务端生效。
- 遗留一：令牌有效期 2 小时、不做滑动续期（契约 §4.2 明确本期不支持长效令牌），
  过期后只能重新登录。这是设计取舍，不是缺陷。
- 遗留二：`session_token` 里记了 `client_ip` 用于审计，但**没有**做"令牌绑定 IP/UA"。
  令牌被窃后换机器仍可用——拦截点是有效期与退出撤销。若 II 阶段要收紧，需在
  `auth.require_auth()` 里加一致性校验，并同步改本表。
