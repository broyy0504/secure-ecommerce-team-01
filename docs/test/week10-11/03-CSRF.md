## 1. 先按任务书的口径定判定

> CSRF：令牌放请求头，或 Cookie 加 SameSite；两者都没有就是没防。令牌走请求头本身就不随表单
> 自动带，这种情况记"由设计规避"并写明理由，不要记成"未覆盖"，也不要记成"已实现防护"。

本系统的形态属于**第三类**：令牌只从 `Authorization: Bearer` 读，`sessionStorage` 存，
全程不下发任何 Cookie。所以：

- 不是"已实现防护"：代码里没有 CSRF token，也没有 `SameSite` 设置，谈不上"实现了某个机制"；
- 不是"未覆盖"：攻击链的第一环（浏览器自动带凭据）在本架构里不存在；
- 是"**由设计规避**"：规避的前提写清楚，前提一变就必须重测。

## 2. 规避成立的理由（三条，缺一不可）

1. **不用 Cookie 承载凭据。** 登录、个人信息、鉴权校验的响应里 `Set-Cookie` 数量为 0（C-02）。
   CSRF 的本质是"浏览器自动把凭据附在跨站请求上"，没有 Cookie 就没有这个自动行为。
2. **令牌在自定义头里，表单带不了。** `<form>` 只能提交 `application/x-www-form-urlencoded`、
   `multipart/form-data`、`text/plain` 三种体，无法设置 `Authorization`。C-01 用跨站表单打退出接口，
   返回 401、会话未被撤销，正是这一步的实测。
3. **CORS 白名单而非 `*`。** 预检只对 `127.0.0.1:8080` / `127.0.0.1:5173` / `localhost:5173` 放行
   （C-03、C-04），
   并且不带 `Access-Control-Allow-Credentials`。即使攻击者让浏览器把请求发出去，
   也读不到响应（C-05）。

**规避的边界（答辩时主动说）：** 只要将来把令牌改成 Cookie 承载——比如为了"记住我"或
同域部署——CSRF 的前提立刻恢复，必须同时补 `SameSite=Lax/Strict` 与双提交令牌，并重跑本表。
这条已写进 `docs/handover/01-用户表与身份字段冻结清单.md` §6 的已知局限。

**为什么 C-03/C-04 必须用 curl 打，不能在页面里用 JS 打：** 浏览器不允许脚本伪造 `Origin` 头。
实测在 Edge 里从 `http://127.0.0.1:5173` 的页面发一个带 `Origin: http://evil.example` 的
`OPTIONS`，浏览器把 `Origin` 换成了自己的源（正好在白名单内），服务端返回 `204`。
这条 `204` **不能**证明"攻击者源被拒"，只证明"浏览器不让脚本改 `Origin`"。
所以跨源预检的两条判定用 curl 直接指定 `Origin` 头，才是对服务端策略的真实检验。

## 3. 需求写漏：一份要交给 II 阶段的整改输入

`docs/threat-model/threat-list.md` 共 31 条威胁，**没有 CSRF**；`02-安全需求.md` 共 20 条 SR，
也没有一条覆盖它。也就是说：本期之所以"没出事"，靠的是架构选型，而不是需求驱动。

这不是"测下来通过就完了"的事，按任务书"指不到就说明当初需求写漏了"的口径，如实登记：

| 项 | 建议登记内容 |
| :--- | :--- |
| 威胁编号（建议） | `T-SP-07`：攻击者诱导已登录用户在第三方站点提交请求，借用户浏览器里的凭据完成状态变更（改资料、退出、下单） |
| 安全需求编号（建议） | `SR-21`：所有状态变更接口的凭据不得由浏览器自动携带；若使用 Cookie，必须 `SameSite` 且校验来源 |
| 判定方式（建议） | 逐接口检查凭据载体；`Set-Cookie` 出现即视为需要 CSRF 控制，必须给出 `SameSite` 或双提交令牌的实测证据 |
| 归属阶段 | II 阶段（引入下单、支付前必须补齐，这两类接口的状态变更有实际损失） |

本期不擅自改第 6-9 周已验收的威胁清单与 SR 清单，只在此登记，随交接契约一并交给 II 阶段。

## 5. 结论

- 结论：本系统**由设计规避** CSRF——无 Cookie、令牌只在自定义头、CORS 白名单。
  C-01～C-05 五条实测支持这个判断，其中 C-01 是"表单打过来也没用"的直接证据。
- 遗留一：CSRF 在威胁清单与安全需求里都是空白，已在 §3 登记建议编号（`T-SP-07` / `SR-21`），
  交 II 阶段补入。**这是本期测试发现的唯一一处需求缺口**。
- 遗留二：规避依赖"不用 Cookie"这个前提。前提变化时必须重测，判定不得沿用本表。
