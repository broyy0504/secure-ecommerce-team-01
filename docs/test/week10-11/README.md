## 3. 判定口径（三类特殊结果怎么写）

任务书对"没防住"和"不需要防"给了明确口径，本记录严格照此填写，不含糊其辞：

| 情形 | 写法 | 本期实例 |
| :--- | :--- | :--- |
| 有控制、实测有效 | 通过 | 注入、XSS、会话劫持、越权 |
| 靠架构形态消除前提 | **由设计规避**（写明前提与失效条件） | CSRF：不用 Cookie，令牌只在 `Authorization` 头 |
| 需求层根本没提 | **未登记**（并给补登记建议） | CSRF 在威胁清单 31 条、SR 20 条里都没有 |

第三条不是"免责声明"，是**交付物的一部分**：它指出了第 6-9 周需求文档的一处缺口，
并在 [`03-CSRF.md`](./03-CSRF.md) §3 给出了建议编号（`T-SP-07` / `SR-21`）与验收方式，
随交接契约交给 II 阶段。

## 6. 已知局限（不掩盖）

1. **限流计数在进程内存**，多实例部署会各算各的，需要换共享存储；本期单进程演示不受影响。
2. **`phone_hash` 是无密钥 SHA-256**：手机号空间有限（约 10¹⁰），拿到库的人可以枚举比对。
   它只解决"不明文落库"，不解决"不可反推"；II 阶段应换成 HMAC 或加密列（见交接契约 §4）。
3. **登录锁定阈值取 5 次 / 10 分钟**，契约里还有一处待裁决（C-04：`SR-AUTH-002` 取 5、
   `FR-USER-007` 取 10）。本期取小值并用 IP 维度限流兜底，对外文案与状态码不随阈值变化。
4. **CSRF 的规避依赖"不用 Cookie"**，一旦引入 Cookie 会话必须重测，判定不得沿用本表。
