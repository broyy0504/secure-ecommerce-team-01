# 攻击树

文档编号：TM-02
2026-10-23

根目标是"以买家身份拿到一个可用会话，然后对他的订单读写"，也就是账户接管。选这个是因为它同时打通 AS-01 和 AS-02、直达 AS-03/AS-04，T-SP-02、T-SP-03、T-TM-02、T-EL-01、T-ID-02、T-ID-04、T-ID-07 全挂在这棵树上，叶子也大多成本低、容易复现。

图例：`AND` 表示下面的子节点都得做到，`OR` 表示任一条路走通就行。

覆盖状态按 `04` §1 的"实现/规定"二分来定：

- **已实现**：`04` §2 里性质写着"实现"，代码能跑能观测。现在只有 CTRL-01～04，全在 `src/crypto/`。
- **设计已覆盖**：有 SR 的可判标准 + `04` 里有规定出处 + 有 R-D 整改条目。
- **部分**：SR 或整改只盖住一部分路径，或者验收缺关键的判定动作。
- **否**：没 SR、没整改、没规定，三样都没有。

成本分档：低（<1 小时、脚本级）、中（1–3 天、要工具或一定权限）、高（要内网、0day 或长期社工）。

## 1. 攻击树

```
G0 以买家身份拿到可用会话，然后操作他的订单
├─ OR G1 拿到买家口令，直接拿口令登录
│  ├─ AND G1.1 先拿到口令派生值（拖库）
│  │  ├─ L1 往注册/登录/下单参数里注入 SQL，读出 user_account      → T-TM-05
│  │  ├─ L2 下载暴露在公网的备份或调试接口                          → T-ID-06
│  │  └─ L3 内部人员导出（越权查询、备份外流）                      → T-SP-01
│  └─ AND G1.2 再离线还原口令
│     ├─ L4 字典/规则爆破弱口令（600k PBKDF2 让单次变贵）           → T-SP-01
│     ├─ L4a 业务代码传了 seed，盐可预测                            → T-ID-07
│     ├─ L4b password_iterations 被配低或者被篡改                   → T-TM-06
│     └─ L5 彩虹表反查（每账号随机盐基本堵死这条路）                → T-SP-01
├─ OR G2 拿到或者伪造令牌，跳过口令
│  ├─ L6 凭空构造/猜令牌                                            → T-SP-03
│  ├─ L6a 改自己令牌一位，或者改编码的用户标识                     → T-TM-02
│  ├─ L6b 读种子，用 rsa.py 复现签名私钥                           → T-SP-06
│  ├─ L6c 用仓库自带 pollard_rho 分解小位宽签名模数                → T-EL-03
│  ├─ L7 用 XSS 读浏览器 Cookie 里的令牌                           → T-ID-03
│  ├─ L8 用户退出后重放旧令牌                                       → T-SP-03
│  └─ L9 从 URL/Referer/历史/访问日志里收集令牌                    → T-ID-03
├─ OR G3 绕过认证逻辑
│  ├─ L10 登录参数注入让条件恒真                                    → T-TM-05
│  ├─ L11 请求体加 role/别人 userId，或者直调商户/管理端接口        → T-EL-01
│  └─ L12 撞库：复用别处泄露的手机号+口令                          → T-SP-02
└─ OR G4 不接管账户，直接越权操作订单
   ├─ L13 遍历 orderId 读别人的订单和收货信息                     → T-ID-04
   ├─ L14 伪造支付成功报文打回调                                   → T-SP-04
   ├─ L15 请求体附单价/总价/状态，让服务端按他给的钱记账           → T-TM-01、T-TM-03
   └─ L16 并发抢最后一件库存，两单都成功                           → T-TM-04
```

## 3. 看完图的几个结论

22 片叶子里，**已实现 1 片（L5）、设计已覆盖 15 片、部分 5 片（L4、L4a、L4b、L6b、L6c）、否 1 片（L2）**。这跟 `04` §1 说的"业务代码里落地的控制 0 条"是一致的——除了 CTRL-01～04，其他控制全在文档层。

**L1/L10（注入）不是"否"**。`04` 里有 CTRL-10 定参数化、R-D-02 是整改、`02` 里 SR-19 是可判标准，问题只出在 SR-19 的源威胁列没写 T-TM-05，链条断在一行上，覆盖状态标成"设计已覆盖，SR 那行没标源"。

**L2（备份/调试暴露）是唯一真"否"**。`02` 没 SR、`04` 没 CTRL 没 R-D，三样都缺，DREAD 7.0 也不低。

**L6b/L6c（签名密钥可复现、小位宽可分解）算"部分"**。R-D-04 盖住了令牌签发，但验收里没有"禁止 import `bigint_ops`/`rsa`、禁止 `JavaRandom`"这一条。

**L4a/L4b（seed/迭代）也是"部分"**。CTRL-03 写了"生产路径不传 seed"，R-D-01 是整改，但验收里没有对应的检索和越界拒绝动作。

**T-EL-02（高权限 DB 账号）不在这棵树上**。它是 L1 得手之后的后利用，挂在 L1 下游，不是独立分支。单独在威胁清单登记了，覆盖状态是"三样都缺"。

**待裁决冲突对这棵树的影响**：C-01（锁定用 401 不用 423）已经跟 SR-04 一致，L12 不受影响；C-02（用 PBKDF2 不换 Argon2id）跟 `加盐哈希.py` 一致，L4/L5 不受影响；C-03（四列）跟 R-D-01 一致。C-04、C-05 还没拍，一个影响 L12 的阈值，一个影响改密撤销的验收。
