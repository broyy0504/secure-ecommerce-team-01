## 2. 先管的 5 条

**1. T-TM-05（8.8）**
唯一一条能同时碰到 AS-01 和 AS-03 的入口，也是 T-SP-01 和 T-EL-02 的上游。堵住这一条，"注入→拖库→破解→撞库"整条链就断了。`04` 里已经有 CTRL-10 和 R-D-02，覆盖不是零；断的是 `02` 的 SR-19 源威胁列没写 T-TM-05。验收好判：全仓搜 SQL 拼接模式，命中 0；带引号或注释符的输入只能当数据。

**2. T-SP-02（8.6）**
不需要任何系统漏洞，门槛最低，直接产出 AS-02。SR-05 + SR-20 + R-D-03 + R-D-06 四重覆盖，改动集中在登录一处，收益大。

**3. T-ID-02（8.4）**
T-SP-02 的前置侦察。SR-04 把"响应体、状态码、耗时三方面不可区分"写成了可判标准，还要求账号不存在时也跑一次同等参数的派生，这条写得很实。注意 C-01 已经拍了：锁定对外统一 `401`，不用 `423`，跟 SR-04 一致。

**4. T-DN-03（8.2）**
600k 迭代是安全收益，同时也是 CPU 放大器。SR-20 + R-D-06 的限流能覆盖，覆盖状态不是空的，只是 SR-20 的源威胁列没写它。排在先管是因为 8.2 分，不是因为没控制。

**5. T-ID-04（8.0）**
改一个数字就能读到别人的收货信息。SR-15 + R-D-07 + CTRL-08 + CTRL-20 四重覆盖，对象级隔离以 `user_id`/`merchant_id` 为边界，这条写法是对的。

**T-SP-01（7.8）为什么没进先管**：`04` 里 CTRL-01～04 是**唯一 4 条性质是"实现"的控制**，全在 `src/crypto/加盐哈希.py`。SR-01/SR-02 和 R-D-01 已经把"四列存储 + 参数不接受请求传入"写成可判标准。剩下的风险在"接入姿势"上（禁用 `seed`、迭代上限），随 R-D-01 落地就行。C-02 已经拍了统一 PBKDF2 不换 Argon2id，C-03 拍了用四列、数据字典要跟着改。
