## 1. 编号规则与写法约定

1. 本文件的安全需求编号为 `SR-01` 起的两位序号，与第 3 周《安全与非功能需求清单V1》的 `SR-DATA-001` 一类"分类前缀"编号是**两套编号**，不互相替代。两套的对应关系见 §6。
2. 每条安全需求必须写清**怎样算通过**：可执行的步骤 + 可观测的对象 + 明确的判定标准。写不出判定的，不作为安全需求，只作为设计建议。
3. 每条安全需求必须指到**至少一个威胁编号**。威胁编号的登记口径见 §2。
4. 每条安全需求标注**落实位置**：已具备的指到仓库文件与章节/行号；未具备的指到 `04` 文件中的整改编号 `R-D-xx`。不存在"应已实现"这种无出处的声明。

## 3. 安全需求

### 3.1 用户凭证（AS-01）

| 编号 | 安全需求 | 怎样算通过 | 源威胁 | 落实位置 |
| :--- | :--- | :--- | :--- | :--- |
| SR-01 | 口令只以"算法标识、迭代次数、盐、派生值"四列存储，四列中不存在任何可逆推出原口令的值，也不存在第五个与口令相关的列 | 空库执行一次注册后，对 `user_account` 做 `SELECT *` 并列出全部列名。判定通过需同时满足：① 与口令相关的列恰好是 `password_algo`、`password_iterations`、`password_salt`、`password_derived` 四列且均非空；② 四列十六进制拼接后与原口令字符串不相等、也不包含原口令；③ 不调用派生函数的情况下，库中任一列都无法复原原口令 | T-SP-01 | 算法具备：`src/crypto/加盐哈希.py` L22-25、L64-71；落库未实现 → **R-D-01** |
| SR-02 | 口令派生参数不低于 PBKDF2-HMAC-SHA256、600000 次迭代、16 字节盐、32 字节派生值；盐由密码学安全随机源生成且每账号唯一；迭代次数与盐不接受请求传入 | ① 查库确认 `password_algo = 'pbkdf2_sha256'`、`password_iterations >= 600000`；② 用同一口令注册两个账号，两行的盐与派生值互不相同；③ 对 1000 个账号的盐做重复统计，重复数为 0；④ 在注册请求体中加入 `iterations`、`salt` 字段，返回 `400` 且不落库 | T-SP-01 | 算法具备：`src/crypto/加盐哈希.py` L22-25、L42、L64-71；参数拒绝未实现 → **R-D-01** |
| SR-03 | 口令原文、派生值、盐不出现在任何应用日志、访问日志、异常响应、监控标签与审计记录中；限流与缓存使用的键必须是账号或地址的哈希，不得是明文 | 分别触发一次成功与失败注册、成功与失败登录，然后全量检索当日日志（应用日志 + 访问日志 + 审计表 + 异常上报）。判定通过需同时满足：① 以注册时使用的口令字符串检索，命中 0；② 以库中该账号的派生值与盐的十六进制串检索，命中 0；③ 响应体与异常上报中没有上述任一值；④ 限流存储中不存在明文账号或手机号 | T-ID-01 | 未实现 → **R-D-11** |
| SR-04 | 登录失败时，"账号不存在"与"口令错误"两条路径在响应体、HTTP 状态码、响应耗时三方面不可区分；账号不存在时仍执行一次同等参数的派生运算 | 准备存在账号 A 与不存在账号 B，各发起 100 次同口令错误登录（控制频率避开限流）。判定通过需同时满足：① 两组响应的 `code` 与 `message` 逐字相同；② 两组状态码相同；③ 两组响应耗时中位数相对差 < 15% | T-ID-02 | 未实现 → **R-D-03** |
| SR-05 | 连续失败达阈值后，服务端拒绝该账号的正确口令；但对外响应仍与普通失败一致，不透露"账号被锁定"；同时按账号与来源 IP 双维度限流加退避，使攻击者无法靠反复试错锁死他人账号 | ① 对账号 A 连续提交错误口令至阈值后，立即用正确口令登录，响应为 `401` 且 `code`、`message` 与普通失败逐字相同；② 查 `login_log`，该次记录的 `failure_code` 为锁定类原因（内部可见）；③ 锁定窗口结束后，正确口令可登录；④ 从另一 IP 对账号 A 继续发力，全局限流生效并返回 `429` | T-DN-01、T-SP-02 | 未实现 → **R-D-03**、**R-D-06** |
