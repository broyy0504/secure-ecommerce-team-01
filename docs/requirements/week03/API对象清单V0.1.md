## 3. 通用约定

1. **基础路径**：统一使用 `/api` 前缀；请求和响应默认使用 `application/json`，字符编码为 UTF-8。
2. **传输安全**：除本地开发环境外，所有接口必须通过 HTTPS/TLS 访问，密码和令牌不得出现在 URL 查询参数中。
3. **身份来源**：登录成功后由后端建立有效会话或签发访问令牌；受保护接口从服务端会话或令牌解析当前用户，不信任客户端提交的 `user_id`、`role` 或资源归属字段。
4. **鉴权原则**：后端同时校验角色权限和资源归属，遵循默认拒绝、最小权限和对象级隔离原则。前端隐藏入口不能代替后端鉴权。
5. **数据最小化**：接口不得返回明文密码、密码哈希、密钥、完整支付凭证或与当前业务无关的个人信息。
6. **错误提示**：登录失败统一提示“账号或密码错误”，不得通过响应差异泄露账号是否存在、是否被锁定等敏感状态。
7. **输入校验**：所有请求参数在服务端校验；数据库查询必须使用参数化方式，不能拼接用户输入。
8. **审计追踪**：登录、退出、密码修改、鉴权失败和敏感操作应记录操作人、时间、对象、结果及请求追踪编号，但日志不得记录密码或令牌。

| API-AUTH-001 | `POST /api/auth/login` | 验证买家、商户或管理员凭据并创建有效会话或令牌 | 已注册且账号可用的内部角色；公开接口 | 参数在服务端校验；错误凭据不得建立会话且提示不泄露账号存在性；同一账号连续失败 5 次后锁定；成功后从服务端读取角色和状态；记录登录结果，不得记录原始密码；商户、管理员未通过审核或被停用时拒绝登录 | FR-USER-002；SR-INPUT-001；SR-AUTH-002；UC-USER-002 |

| API-USER-004 | `PUT /api/users/me/password` | 修改当前用户密码，保障账号凭据可安全轮换 | 已登录用户；需要本人有效凭据 | 必须校验旧密码并满足新密码强度要求；新密码加盐不可逆存储；响应和日志不得出现旧密码或新密码；修改成功后可统一使其他会话失效，至少应回收本次操作外的陈旧凭据 | FR-USER-006；SR-DATA-001；SR-LOG-001；UC-USER-006 |

### 4.1 P0 直接引用的数据对象

本版只说明 API 与数据对象的依赖关系，不设计字段：

- 用户、角色、用户角色关系：注册、身份识别和角色授权。
- 会话或令牌：登录成功后建立、受保护接口校验、退出后失效。
- 登录日志：记录成功或失败结果、失败次数与锁定依据。
- 个人资料：个人中心查询和允许范围内的修改。

## 7. 状态码与错误语义基线

| 状态码 | 使用场景 | 约束 |
| --- | --- | --- |
| `200 OK` | 查询、修改、登录、退出成功 | 返回必要业务结果，不返回敏感字段 |
| `201 Created` | 注册等资源创建成功 | 可返回资源标识和最小公开资料 |
| `204 No Content` | 退出、删除等无响应体操作 | 仅用于确实无需返回业务数据的情况 |
| `400 Bad Request` | 参数缺失、格式错误、非法状态 | 返回稳定业务错误码和友好提示，不返回堆栈 |
| `401 Unauthorized` | 未登录、凭据无效、会话失效 | 登录失败提示不得泄露账号是否存在 |
| `403 Forbidden` | 已登录但角色或资源权限不足 | 后端拒绝并记录越权尝试，不依赖前端拦截 |
| `404 Not Found` | 资源不存在或按安全策略隐藏越权资源 | 不得泄露其他用户、商户或内部资源信息 |
| `409 Conflict` | 登录名、手机号等唯一信息冲突 | 注册场景需给出可操作提示 |
| `423 Locked` | 连续登录失败导致账号锁定 | 锁定规则和提示需与安全需求保持一致 |
| `429 Too Many Requests` | 登录或注册请求超过限流阈值 | 防止暴力破解和批量注册 |
| `500 Internal Server Error` | 未预期服务异常 | 只返回统一友好提示和追踪编号，不暴露堆栈或数据库信息 |

具体响应体结构在 V0.2 与后端实现方案统一后补充。V0.1 要求所有接口至少具备统一的业务错误码、用户可读提示和可追踪请求编号。

## 8. 安全与验收检查点

1. 注册、登录、退出、本人信息查询和修改接口均已列入清单，覆盖用户管理核心功能。
2. 受保护接口均明确登录要求和资源归属边界；客户端提交的用户编号、角色和资源归属不能直接作为授权依据。
3. 密码在传输、存储、日志和接口响应中均受到保护；退出后的旧凭据不得继续访问受保护接口。
4. 连续登录失败、参数校验、SQL 注入和越权访问均应具有可执行的正向或反向验收方法。
5. P0、P1、P2 边界清晰，后续新增接口不得擅自扩大 Project I 的必做范围。
6. API 编号、需求编号和用例编号在第 4 周评审前完成最终核对，并同步到需求追踪矩阵。

## 9. 待确认事项

1. 登录凭据采用服务端会话还是访问令牌；该选择影响响应头和失效机制，但不影响本清单的 API 对象边界。
2. 用户注册标识最终采用用户名、手机号还是二者组合；本清单按“至少一种唯一登录标识”编写。
3. 个人信息允许修改的字段范围，需要与数据对象清单和个人中心界面保持一致。
4. 支付相关接口最终归入 Project I 的可选扩展还是项目 II、III；当前按“预留、不参与 V0.1 验收”处理。
5. FR、UC、SR 编号以其他需求文件最终版本为准；如编号调整，应同步更新本清单和需求追踪矩阵。
