## 3. II 阶段接手的顺序（按依赖排）

1. 读 `01`，确认 `user_account` 的 15 列与 7 项身份字段，**不要改**；
2. 读 `02`，按 DDL 草案建 `order_header`，外键指向 `user_account.user_id`；
3. 读 `03` §3.1—3.5，实现商品与购物车（它们不依赖订单）；
4. 读 `03` §3.6—3.7，实现下单与订单查询（依赖 `02` 的主键与 `01` 的用户表）；
5. 读 `03` §3.8，实现支付回调（依赖 `02` 的 `order_no`）；
6. 角色矩阵与 §3.9 证书认证最后做，它们会动到 `app_role` 表。

## 4. 三条不能破的约定

1. **只加不改**：用户表与订单主键的名称、类型、含义定稿。新增字段可以，改名/改类型不行。
   要改，写变更记录并升版本号，同时改 `db/schema.sql`、`src/user/db.py`、`openapi.yaml` 三处。
2. **未实现就说未实现**：不准用空数组、假数据、200 空对象冒充实现；501 + 固定文案。
3. **身份只有一个来源**：`Authorization: Bearer`。II 阶段任何新接口都必须调用同一个
   `src/user/auth.py` 的 `require_auth()`，不得自己解析请求头。

## 5. 交给 II 阶段时一并说明的三处遗留

| 遗留 | 影响 | 建议 |
| :--- | :--- | :--- |
| CSRF 在威胁清单与安全需求里均未登记 | 目前靠"不用 Cookie"规避；一旦改 Cookie 会话就裸奔 | 按 `docs/test/week10-11/03-CSRF.md` §3 补 `T-SP-07` / `SR-21` |
| `phone_hash` 为无密钥 SHA-256 | 拿到库的人可枚举出手机号 | 改 HMAC 或加密列，列名不变 |
| 限流计数在进程内存 | 多实例部署时阈值不准 | 换 Redis 一类共享计数 |

这三条都写进了 `01` §6，此处只做提醒：它们不是"以后再说"，是 II 阶段动手前要先决定的事。
