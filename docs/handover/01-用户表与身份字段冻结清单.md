## 1. 为什么这份清单必须先冻结

任务书的原话是"不得在 II 阶段重新定义核心订单主键和身份字段"。这句话的现实含义是：
II 阶段会写订单、支付、商品三块代码，这三块**全都要读 `user_id`**。如果那时用户表的主键叫法
或类型变一次，II 阶段所有涉及用户的查询、外键、索引都要跟着改，等于返工。

本期的做法：把"用户表长什么样"从"某个人脑子里的约定"变成"一份能被别人照着写代码的文件"，
并把差异（MySQL 与 SQLite）也写进来，避免 II 阶段发现两套库对不上。

## 2. 用户表 `user_account`

表名固定为 `user_account`（单数、下划线）。**不是** `users`、**不是** `User`。
第 10 周之前仓库里同时存在 `users`（`src/user/db.py`）与 `user_account`（`db/schema.sql`）两个叫法，
本期统一到 `user_account`，见 §5 C-02。

| 序号 | 字段名 | 逻辑类型 | 可空 | 默认 | 含义 | 对外可见 |
| :---: | :--- | :--- | :---: | :--- | :--- | :--- |
| 1 | `user_id` | 整数，自增主键 | 否 | 自增 | 用户唯一标识，**全库唯一的用户主键**；订单、支付、角色关系表都引用它 | 是（字符串形式） |
| 2 | `username` | 字符串 ≤ 32 | 否 | — | 登录名，唯一；`^[A-Za-z0-9_]{4,32}$` | 是 |
| 3 | `password_algo` | 字符串 ≤ 32 | 否 | `pbkdf2_sha256` | 口令派生算法标识 | **否** |
| 4 | `password_iterations` | 整数 | 否 | — | PBKDF2 迭代次数，≥ 600000 | **否** |
| 5 | `password_salt` | 字符串，22 字符 | 否 | — | 16 字节盐的 base64url（无填充） | **否** |
| 6 | `password_derived` | 字符串，43 字符 | 否 | — | 32 字节派生值的 base64url（无填充） | **否** |
| 7 | `phone_hash` | 字符串，64 字符 | 否 | — | `SHA-256("bookstore:phone:" + 归一化手机号)`，用于唯一约束与登录查号 | **否** |
| 8 | `phone_masked` | 字符串 ≤ 16 | 否 | — | 展示用脱敏手机号，如 `138****8000` | 是 |
| 9 | `nickname` | 字符串 ≤ 32 | 是 | 取 `username` | 昵称，**原文存储**，输出侧转义 | 是 |
| 10 | `status` | 枚举 | 否 | `active` | `active` 正常 / `locked` 锁定 / `disabled` 停用 | 是（仅本人可见取值） |
| 11 | `failed_login_count` | 整数 ≥ 0 | 否 | 0 | 连续登录失败次数，成功即清零 | **否** |
| 12 | `locked_until` | 时间 | 是 | NULL | 锁定到期时间；NULL 或已过期即未锁 | **否** |
| 13 | `last_login_at` | 时间 | 是 | NULL | 上次成功登录时间（本次登录前） | 是 |
| 14 | `created_at` | 时间 | 否 | — | 注册时间，**不可修改** | 是 |
| 15 | `updated_at` | 时间 | 否 | — | 最近一次改动时间 | **否** |

约束（三处实现必须一致）：

- `username` 唯一；`phone_hash` 唯一；
- `CHECK (status IN ('active','locked','disabled'))`、`CHECK (failed_login_count >= 0)`；
- `CHECK (length(password_salt) = 22)`、`CHECK (length(password_derived) = 43)`、
  `CHECK (password_algo = 'pbkdf2_sha256')`、`CHECK (password_iterations >= 600000)`；
- `user_id` **不对外裸露为整数**，接口里一律以字符串形式给出（`"1"`），避免前端做算术、也避免类型歧义。

## 3. 身份字段（II 阶段不得改动的那 7 项）

任务书点名冻结的身份字段是"账号、口令四列、状态、创建时间"，落到本表就是下面 7 列：

| 身份字段 | 字段名 | 类型 | 冻结内容 |
| :--- | :--- | :--- | :--- |
| 账号 | `username` | 字符串 ≤ 32 | 名称、格式 `^[A-Za-z0-9_]{4,32}$`、唯一约束 |
| 口令（1/4） | `password_algo` | 字符串 ≤ 32 | 固定 `pbkdf2_sha256`，换算法必须走变更记录 |
| 口令（2/4） | `password_iterations` | 整数 | ≥ 600000；只允许调大 |
| 口令（3/4） | `password_salt` | 22 字符串 | 16 字节盐的 base64url；每账号唯一，由 CSPRNG 生成 |
| 口令（4/4） | `password_derived` | 43 字符串 | 32 字节派生值；**不得**出现第五个与口令相关的列 |
| 状态 | `status` | 枚举 | 三个取值与语义固定；新增取值必须走变更记录 |
| 创建时间 | `created_at` | 时间 | 注册时刻，只写一次，不随任何更新变化 |

**"不得重新定义"的具体含义**（II 阶段照这个执行）：

1. 不得把 `user_id` 改成 UUID、字符串或复合主键；
2. 不得把 `username` 改成 `login_name`、`account`、`user_name` 等别名；
3. 不得把口令四列合并成一个 `password` 列（合并即破坏 SR-01 的"四列可分别审计"）；
4. 不得给 `status` 增加 `deleted` 一类取值来代替软删除——`deleted_at` 是另一列的事（见 §4）；
5. 可以在末尾**追加**新列（例如 `email_ciphertext`、`avatar_url`、`deleted_at`），追加后同步本文件。

## 5. 变更记录（相对第 6-9 周基线）

| 编号 | 变更 | 原状 | 现状 | 理由 | 影响面 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| C-01 | 注册接口新增可选字段 `nickname` | 契约 §4.1 只允许 `username/phone/password` | 允许 `nickname`，1—32 字符，缺省取 `username` | 任务书要求 XSS 验收"把带 alert(1) 的 script 标签存进昵称"；`db/schema.sql` 本就有 `nickname` 列，只是接口没开 | `validation.py`、`openapi.yaml`、`web/register.html` |
| C-02 | 表名统一为 `user_account` | SQLite 用 `users`，MySQL 用 `user_account` | 统一 `user_account`；列名同步（`id`→`user_id`） | 避免 II 阶段接手两份不一样的表 | `src/user/db.py`、`src/user/auth_service.py` |
| C-03 | 手机号存储方式 | MySQL 用 `phone_ciphertext` + `phone_hash` | SQLite 只存 `phone_hash` + `phone_masked`，不存明文与密文 | 本期无密钥管理组件；系统不需要读回完整手机号（对外只有脱敏值），少一份密文就少一处泄露面 | 见 §6 局限 2 |

## 6. 已知局限（II 阶段接手前必须知道）

1. **MySQL 与 SQLite 的物理差异**：`phone_ciphertext`、`email_ciphertext`、`email_hash`、
   `avatar_url`、`deleted_at`、`token_family_id`、`login_log.user_agent` 这几列在 SQLite 里**没有**。
   它们属于 II 阶段的扩展位，加列即可，不需要改已有列。
2. **`phone_hash` 是无密钥 SHA-256**：手机号空间约 10¹⁰，拿到库的人可以枚举比对出明文手机号。
   它只解决"不明文落库"，不解决"不可反推"。II 阶段若要收紧，改为 HMAC（密钥进密钥管理）
   或加密列（对齐 `db/schema.sql` 的 `phone_ciphertext`），**列名不变、只换内容编码**。
3. **角色表未落**：`app_role`、`user_role_relation` 本期不建、不写；所有用户角色由常量 `buyer` 提供。
   II 阶段接入时必须用 §2 的 `user_id` 作外键，不得另建 `user_role.user_id` 变体。
4. **限流计数在进程内存**（`src/user/ratelimit.py`）：多实例部署各算各的，需换共享存储。
   与表结构无关，但影响"多实例后锁定/限流是否还准"这个判断。
5. **`email` 不采集**：接口里 `emailMasked` 固定 `null`。要加邮箱，走追加列 + 变更记录，
   不要在 `nickname` 里塞邮箱。
